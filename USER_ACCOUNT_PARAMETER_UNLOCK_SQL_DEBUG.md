# USER_ACCOUNT_PARAMETER_UNLOCK — Oracle SQL & Debugging Guide

## Purpose
This document contains the current Oracle SQL reconstructed from the Ab Initio graph, the confirmed business rules, and step-by-step debugging SQL to identify why the current query returns zero records.

> **Important:** The current SQL is a reconstruction. The debugging section should be used to prove each relationship before treating it as the final 1:1 Ab Initio equivalent.

## Confirmed Business Rules
- All graph joins are INNER JOINs.
- `T_ACCOUNT` has a Remove Duplicates step.
- Duplicates in `T_ACCOUNT` are removed using `ACCOUNT_NO`.
- `DISTINCT_ACCOUNT_ID_COUNT` is `COUNT(DISTINCT ACCOUNT_ID) OVER (PARTITION BY USER_ID)`.
- The first seven output columns are sourced from `T_ACCOUNT` / derived from it:
  1. `ACCOUNT_NO`
  2. `COMPANY_ID`
  3. `HOGAN_PRODUCT_CD`
  4. `SUBPRODUCT_CODE`
  5. `ACCOUNT_ID`
  6. `DISTINCT_ACCOUNT_ID_COUNT`
  7. `USER_ACCOUNT_STATUS`
- `ECN` and `XA_ID` are from `T_USER`.
- The correct status column is `USER_ACCOUNT_STATUS`; there is no `ACCOUNT_STATUS`.
- Contact-type columns are excluded for now.

# Current Reconstructed Query

```sql
WITH T_ACCOUNT_DEDUP AS
(
    SELECT *
    FROM
    (
        SELECT
            A.*,
            ROW_NUMBER() OVER
            (
                PARTITION BY A.ACCOUNT_NO
                ORDER BY A.ACCOUNT_ID
            ) AS RN
        FROM T_ACCOUNT A
    )
    WHERE RN = 1
)
SELECT
    A.ACCOUNT_NO,
    A.COMPANY_ID,
    A.HOGAN_PRODUCT_CD,
    A.SUBPRODUCT_CODE,
    A.ACCOUNT_ID,

    COUNT(DISTINCT A.ACCOUNT_ID)
        OVER (PARTITION BY U.USER_ID) AS DISTINCT_ACCOUNT_ID_COUNT,

    UA.USER_ACCOUNT_STATUS,

    U.USER_ID,
    UAS.MESSAGE_TYPE_ID,
    UAS.ACTIVE_IND AS SUBSCRIPTION_IND,

    UA.PMC_IND,
    UA.PRODUCT_CODE,
    UA.PREFERRED_LANGUAGE,

    U.XA_ID,
    U.ECN,

    UASP.SUBSCRIPTION_PARAMETER_ID,
    UASP.PARAMETER_VALUE,
    UASP.CREATOR_ID,
    UASP.CREATE_DATE,
    UASP.MODIFIER_ID,
    UASP.MODIFY_DATE,

    SP.PARAMETER_NAME,
    SP.PARAMETER_DESC,
    SP.PARAMETER_DATATYPE

FROM T_USER U

INNER JOIN T_USER_ACCOUNT UA
    ON U.USER_ID = UA.USER_ID

INNER JOIN T_ACCOUNT_DEDUP A
    ON UA.ACCOUNT_ID = A.ACCOUNT_ID

INNER JOIN T_USER_SUB US
    ON US.USER_ID = U.USER_ID

INNER JOIN T_USER_ACCOUNT_SUB UAS
    ON UAS.USER_ID = UA.USER_ID
   AND UAS.ACCOUNT_ID = UA.ACCOUNT_ID
   AND UAS.MESSAGE_TYPE_ID = US.MESSAGE_TYPE_ID

INNER JOIN T_MESSAGE_TYPE MT
    ON MT.MESSAGE_TYPE_ID = UAS.MESSAGE_TYPE_ID

INNER JOIN T_USER_ACCOUNT_SUB_PARAMETER UASP
    ON UASP.USER_ID = UAS.USER_ID
   AND UASP.ACCOUNT_ID = UAS.ACCOUNT_ID
   AND UASP.MESSAGE_TYPE_ID = UAS.MESSAGE_TYPE_ID

INNER JOIN T_SUB_PARAMETER SP
    ON SP.SUBSCRIPTION_PARAMETER_ID =
       UASP.SUBSCRIPTION_PARAMETER_ID;
```

> Do not add `WHERE ACCOUNT_STATUS = 'ACTIVE'` or `ACTIVE_IND = 'Y'` at this stage. No such final filter has been confirmed.

# Sequential Debugging

Recommended order:

1. Individual table counts.
2. `T_USER -> T_USER_ACCOUNT`.
3. `T_USER_ACCOUNT -> T_ACCOUNT`.
4. `T_ACCOUNT` duplicate analysis.
5. `T_USER_ACCOUNT -> T_USER_ACCOUNT_SUB`.
6. `T_USER_ACCOUNT_SUB -> T_MESSAGE_TYPE`.
7. `T_USER_ACCOUNT_SUB -> T_USER_ACCOUNT_SUB_PARAMETER`.
8. `T_USER_ACCOUNT_SUB_PARAMETER -> T_SUB_PARAMETER`.
9. Complete join **without** `T_USER_SUB`.
10. Add `T_USER_SUB` back and compare.

The most useful results to bring back are:

```text
T_USER = ?
T_USER_ACCOUNT = ?
T_ACCOUNT = ?
T_USER_SUB = ?
T_MESSAGE_TYPE = ?
T_USER_ACCOUNT_SUB = ?
T_USER_ACCOUNT_SUB_PARAMETER = ?
T_SUB_PARAMETER = ?

USER -> USER_ACCOUNT = ?
USER_ACCOUNT -> ACCOUNT = ?
USER_ACCOUNT -> USER_ACCOUNT_SUB = ?
USER_ACCOUNT_SUB -> MESSAGE_TYPE = ?
USER_ACCOUNT_SUB -> UASP = ?
UASP -> SUB_PARAMETER = ?

Complete WITHOUT T_USER_SUB = ?
Complete WITH T_USER_SUB = ?
```

This will identify the exact join that is eliminating the rows instead of changing joins or adding filters blindly.
